000016_cluster_allow_insecure_tls (F#5 security audit 2026-05-22)
------------------------------------------------------------------------

Adds the `allow_insecure_tls` boolean column on `clusters` and replaces the
silent "no CA → skip TLS verification" fallback in cluster_router with an
explicit fail-closed check. The backfill of existing CA-less rows lives in
the separate 000017 migration (see below for why).

Operator action required:

  - If you registered remote clusters BEFORE upgrading to the schema that
    includes 000016 + 000017, and those rows had NO CA certificate (auth/
    storage paths that stored an empty ca_data column), 000017 auto-flags
    them as `allow_insecure_tls = true` to preserve connectivity. This is
    the same effective security posture they had pre-upgrade (insecure
    TLS), but it is now visible and opt-out instead of silent and on by
    default.

  - Review the auto-flagged rows in the cluster list. The UI surfaces a
    red "⚠ Insecure TLS" badge next to each non-local cluster whose
    `allow_insecure_tls` is true.

  - Inspection query (paste into psql against the kubecenter database):

      SELECT id, name, api_server_url
        FROM clusters
       WHERE allow_insecure_tls = true
         AND is_local = false
       ORDER BY name;

  - For each flagged row, either:
      (a) Provide a CA certificate via re-registration / credential update
          and then explicitly toggle `allow_insecure_tls = false`; or
      (b) Accept the insecure flag explicitly. SECURITY CAVEAT: bearer
          tokens traverse an unverified TLS connection — only appropriate
          for isolated homelab networks. A network-adjacent attacker can
          intercept the bearer and decrypt every subsequent k8s API call.
          The accepted-risk posture is logged at registration time
          (slog Warn) and re-emitted on every applyClusterTLS call.

  - The local cluster row (is_local = true) is skipped by the backfill —
    in-cluster TLS uses the service-account CA bundle from the pod, not
    the stored ca_data column.

Binary-rollback constraint (READ BEFORE RUNNING 000016.down.sql):

  Running `migrate down` against a database whose backend pods include
  the F#5 fix WILL crash every cluster API call. ClusterStore.List/Get
  unconditionally SELECT allow_insecure_tls, and applyClusterTLS in
  cluster_router.go consumes the field on every remote rest.Config build.
  The full runbook lives in 000016_cluster_allow_insecure_tls.down.sql;
  the short version is: stop post-F#5 pods, run 000017.down then
  000016.down, then deploy a pre-F#5 backend image (which reintroduces
  the silent TLS-skip vulnerability F#5 was designed to close).

  There is no safe rollback path that retains the F#5 protection.

000017_backfill_allow_insecure_tls (F#2 round-3 security audit 2026-05-23)
------------------------------------------------------------------------

Backfills `allow_insecure_tls = true` on existing CA-less non-local rows
so deployments that registered remote clusters before F#5 stay connected
after the upgrade.

Why a separate migration instead of editing 000016 in place?

  golang-migrate skips migration versions that are already recorded in
  schema_migrations. A round-1 deployment that had applied the original
  (column-add-only) 000016 will NOT re-run the file after the in-place
  edit added the backfill UPDATE — schema_migrations already records
  000016 as applied. Result: those deployments would silently start
  failing every remote-cluster API call as soon as the post-F#5 backend
  rolled out. Splitting the backfill into 000017 forces every deployment
  to run it regardless of which round of 000016 they applied first.

The down migration is an intentional no-op — there is no way to know
which rows the backfill originally flagged versus which the operator
later set explicitly. The destructive operation lives in 000016.down.sql;
see the binary-rollback constraint above before running it.

app_settings is a singleton — test suites must serialize on it
------------------------------------------------------------------------

000002 defines app_settings as a true singleton:

  id INTEGER PRIMARY KEY DEFAULT 1 CHECK (id = 1)

plus a seeded row, so exactly one row can ever exist.

This matters for the PostgreSQL test harness in ../testdb_test.go. That
harness deliberately never drops the schema and never truncates, and
isolates suites by a unique-per-test identifier instead. That works for
every other table in this schema, because each one's uniqueness includes
a column the test controls — an owner id, a cluster id, or a natural key
the test picks.

app_settings is the sole exception. There is no scoping key, so two
suites that write settings collide unconditionally, and whatever one
leaves behind is visible to every later test.

No suite writes settings today. If you add one, serialize it against
other settings suites with a session-scoped advisory lock
(SELECT pg_advisory_lock(hashtext('app_settings'))) released via
t.Cleanup, and restore the row you changed. Do not reach for TRUNCATE —
it races every other suite sharing the database.

If you add a new table, prefer giving it an owner or cluster column so
it falls under the normal unique-id isolation rule rather than becoming
a second exception.

000019_add_dashboard_layout_kind (Release G dashboard builder 2026-09-13)
------------------------------------------------------------------------

Adds 'dashboard_layout' to the user_preferences.kind CHECK. Additive: no
columns change, nothing is backfilled, and no existing row is touched.

Operator action required:
  None on the way up, on any database this project created.

  The up migration first checks that the CHECK it is about to replace is
  actually named user_preferences_kind_check, and stops with that name in the
  error if it is not. That only happens on a database where the constraint was
  renamed out of band; dropping it by a name nothing holds would otherwise be
  a silent no-op, leaving the old narrow CHECK rejecting every dashboard
  layout while the migration recorded clean. If you hit it:

      SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
       WHERE conrelid = 'user_preferences'::regclass AND contype = 'c';

  drop whichever constraint holds the kind CHECK, then re-run. A failed up
  leaves the version dirty at 19 the same way the refused rollback below
  does, so force it back to 18 before re-running:

      migrate -path <migrations> -database <url> force 18

Rollback:
  The down migration narrows the CHECK and WILL FAIL if any dashboard_layout
  row still exists. This is deliberate -- a rollback that silently deleted
  every user's dashboard is worse than one that stops. Inspect first:

      SELECT owner_id, cluster_id, dedup_key, updated_at
        FROM user_preferences WHERE kind = 'dashboard_layout';

  and remove them explicitly if the rollback is intended:

      DELETE FROM user_preferences WHERE kind = 'dashboard_layout';

  IMPORTANT -- the refused rollback leaves the version table dirty. Recover
  before restarting the backend:

      The schema is untouched (PostgreSQL runs the down file's statements in
      one implicit transaction, so the DROP CONSTRAINT rolls back with the
      ADD that failed), but golang-migrate records the attempt before it
      runs, so schema_migrations is left at version 18 with dirty = true
      while the schema is really still at 19. The backend calls m.Up() on
      start, which refuses on a dirty version, so the pod will crash-loop
      until the version is corrected:

          migrate -path <migrations> -database <url> force 19

      or, equivalently, against the database directly:

          UPDATE schema_migrations SET version = 19, dirty = false;

      Do that first, then decide about the layout rows. The same applies in
      reverse if you clear the rows and the rollback then succeeds: nothing
      to force, because that run completes normally.

Locking:
  Recreating a CHECK constraint takes ACCESS EXCLUSIVE on user_preferences
  while PostgreSQL validates the whole table. Milliseconds on a normal
  preferences table; use a maintenance window on a very large one.

000020_scope_eso_history (Release B ESO evidence, U13, 2026-09-22)
------------------------------------------------------------------------

Index-only. Replaces the cluster-blind sync-history dedup key
UNIQUE (uid, attempt_at) with UNIQUE (cluster_id, uid, attempt_at), adds the
keyset-pagination index (cluster_id, uid, attempt_at DESC, id DESC), and drops
the (uid, attempt_at DESC) index that no query uses any more. No columns
change and nothing is backfilled: cluster_id has been NOT NULL DEFAULT 'local'
since 000011 and the poller has always bound it, so no row is unstamped.

Why: a cluster restored from a Velero backup into a second registered cluster
reproduces identical object UIDs. Under the old key the second cluster's sync
attempts collided with the first's and were silently discarded by
ON CONFLICT DO NOTHING, merging two timelines into one.

Operator action required:
  None on the way up. The new unique index is strictly weaker than the one it
  replaces, so it cannot fail on existing data.

  Ship the binary and the migration together. The backend's INSERT names
  (cluster_id, uid, attempt_at) as its conflict target, and PostgreSQL refuses
  a conflict target no unique index matches (SQLSTATE 42P10). A new binary on
  an unmigrated database cannot happen in practice -- the backend migrates on
  start -- but an OLD binary on a MIGRATED database fails every history insert
  the same way. Two situations produce that pairing:

  1. The upgrade itself. The chart's backend Deployment uses the default
     RollingUpdate strategy, so the new pod starts, migrates, and drops the
     old (uid, attempt_at) index while the old pod is still running. Until
     the old pod terminates, its ESO poller logs
       "externalsecrets poller: history insert failed ... (SQLSTATE 42P10)"
     on every attempt it tries to record. Nothing crashes and no row is
     written wrongly. History is only at risk for a sync attempt that the
     old pod alone observed AND that was superseded before the new pod's
     first poll: the new pod starts with no memory of prior attempts, so its
     first tick records every ExternalSecret's current attempt. With a 60s
     poll and an overlap of well under a minute, that needs an
     ExternalSecret refreshing faster than the rollout, and it costs one
     timeline entry, not the timeline.

     To avoid the window entirely, stop the old pod before the new one
     migrates:

         kubectl -n <ns> scale deploy/<fullname>-backend --replicas=0
         helm upgrade <release> ... (restores replicaCount)

     <fullname> is the chart's kubecenter.fullname: the release name when it
     already contains "kubecenter", otherwise <release>-kubecenter.
     `kubectl -n <ns> get deploy` shows it.

     This is a one-time concern for the 000019 -> 000020 upgrade; no later
     migration inherits it.

  2. A binary-only rollback. Roll the migration back with the binary, or not
     at all.

  Why one migration and not an expand/contract pair across two releases: the
  old index cannot coexist with the cluster-scoped key. Kept, it goes on
  rejecting the second cluster's attempts (the bug this migration fixes), and
  the new binary's INSERT would then fail with a unique violation instead of
  deduplicating. A split would only move the same window to the second
  release.

Legacy rows after a KUBECENTER_CLUSTERID change:
  History rows carry the cluster id that was configured when they were
  written. If the local cluster id was ever changed, rows from before the
  change stay under the old id and are invisible to the cluster-scoped reads.
  They are deliberately NOT rewritten: an UPDATE cannot tell a renamed cluster
  from a genuinely different one, and guessing would attribute one cluster's
  history to another. Those rows age out under the normal 90-day retention.

Rollback:
  The down migration recreates the stricter UNIQUE (uid, attempt_at) and WILL
  FAIL if two clusters ever recorded the same (uid, attempt_at). Find them
  first:

      SELECT uid, attempt_at, count(DISTINCT cluster_id)
        FROM eso_sync_history GROUP BY 1, 2
      HAVING count(DISTINCT cluster_id) > 1;

  There is no automatic resolution. Deleting either side destroys one
  cluster's audit trail, so choose which rows go and delete them explicitly.

  A refused rollback leaves the version table dirty at 19 while the schema is
  still at 20 (the file runs in one implicit transaction, so its statements
  roll back together, but golang-migrate records the attempt first). The
  backend refuses to start on a dirty version. Correct it before restarting:

      migrate -path <migrations> -database <url> force 20

  or UPDATE schema_migrations SET version = 20, dirty = false;

Locking:
  golang-migrate wraps each file in a transaction, so CREATE INDEX
  CONCURRENTLY is unavailable. The two builds take a SHARE lock that blocks
  writes to eso_sync_history for their duration: seconds at the table's
  stated steady state of about 2M rows. The single-replica poller is the only
  writer, and an insert blocked past its tick is re-observed on the next one.

000021_add_nc_notification_resource_uid (pre-existing defect #2, 2026-10-02)
------------------------------------------------------------------------

Adds nc_notifications.resource_uid (TEXT NOT NULL DEFAULT ''). The
notification dedup lookup now keys on cluster and UID as well as source,
kind, namespace, name and title, so a same-named resource failing on two
clusters, or a resource deleted and recreated under a new UID, produces its
own notification instead of being suppressed for 15 minutes.

Operator action required:
  None. The column is additive with a constant default (catalog-only on
  PostgreSQL 11+, no table rewrite), and nothing is backfilled.

Behaviour across the upgrade:
  - Rows written before the upgrade carry cluster_id '' and resource_uid ''.
    An empty cluster id has always meant the local cluster, and the dedup
    query folds '' onto 'local', so those rows keep suppressing local
    repeats and never suppress a remote cluster's events.
  - The UID compares exactly. A pre-upgrade row (resource_uid '') does not
    suppress a post-upgrade notification that carries a UID for the same
    resource, so the first 15-minute window after the upgrade can produce one
    repeat per still-failing resource. This is deliberate: the service
    prefers a duplicate to a dropped notification.
  - The feed API gains an optional resourceUid field. It is additive and
    omitted when empty; existing web and mobile clients ignore it.

Rollback:
  The down migration drops the column and cannot fail on existing data; the
  only loss is the recorded UIDs. Roll the binary back first or together:
  the new binary's INSERT names resource_uid and fails once it is gone.

000022_create_backup_assurance (Release F backup assurance, U32, 2026-10-03)
------------------------------------------------------------------------

Creates four new tables for the backup assurance state machine (KTD11):
backup_assurance_policies, backup_assurance_exceptions,
backup_assurance_deliveries and backup_assurance_collector_lease. Purely
additive: no existing table, column, index or row is touched.

Operator action required:
  None on the way up. The migration creates no policy rows, and no policy
  means no evaluation: installing or upgrading never starts raising backup
  exceptions until an administrator configures a policy.

Retention:
  Resolved exceptions become eligible for pruning 90 days after they
  resolve (store.BackupAssuranceExceptionRetention), matching the Notification
  Center's 90-day feed retention. Open exceptions are never pruned, however
  old they are: an exception stays open for as long as its condition holds.

Scope:
  The migration touches no Velero CRD and no nc_* table. The Notification
  Center and the existing Velero (/backup) pages are unaffected in either
  direction.

Deleting a policy discards its history:
  backup_assurance_exceptions cascades from backup_assurance_policies, and
  backup_assurance_deliveries cascades from backup_assurance_exceptions.
  Deleting a policy through the API therefore intentionally removes every
  exception (open and resolved) recorded under it, together with their
  delivery records. Export anything you need to keep before deleting.

Rollback:
  The down migration drops all four tables and cannot fail on existing
  data, but it DESTROYS open-exception state. The collector keeps no
  in-memory copy, so on the next start after a rollback-and-reapply it
  re-opens every condition that is still true and notifies each one exactly
  once more. Expect one repeat notification per still-failing backup
  subject; that is the correct behaviour, not a defect. Roll the binary back
  first or together: a binary that includes the assurance store fails every
  assurance read and write once the tables are gone.

000023_create_change_receipts (Release E tracked changes, U27, 2026-10-04)
------------------------------------------------------------------------

Creates two new tables: change_receipts and change_receipt_grants. Purely
additive: no existing table, column, index or row is touched. (The plan
reserved 000021; 000021 and 000022 were taken by the time this landed.)

What the table stores:
  One row per tracked apply: the owner, the target cluster and its pin
  generation, a "sha256:<hex>" digest of the submitted bundle, the document
  count, and per-object references and outcomes (group/version/resource/
  kind/namespace/name/uid, action, error, errorClass). Verification evidence
  is stored as an opaque JSON array of check results; a final
  verification_state is never replaced (SetVerification guards the UPDATE),
  so the first final verdict wins.

What it emphatically does NOT store:
  No manifest, no spec, no data, no stringData and no rendered YAML, for
  tracked or untracked applies, Secret-bearing or not. contains_secret
  records only that the bundle held at least one kind: Secret document.
  What is actually enforced: the store types have no field for manifest
  content, and a Go reflection test (TestReceiptObject_NeverCarriesManifestFields
  and TestChangeReceipt_NeverCarriesManifestFields) fails if one is added.
  What is not: the free-form per-object error string is written by the
  tracked-apply layer and may echo submitted values from admission or
  validation messages. Filtering it (to its Kubernetes reason class for
  Secret-bearing bundles) happens at read time, per plan D2; keeping raw
  Secret text out of it is that layer's responsibility, not the store's.

The primary key is client-supplied:
  change_receipts.id is the client's operation id, which is what makes a
  retry after a dropped response detectable. It is attacker-influenceable
  in shape, so the HTTP handler constrains it to a UUIDv4 before it reaches
  the store; the column itself is just UUID.

Retention:
  The store provides Cleanup(retentionDays), a DELETE-WHERE sweep on
  created_at. The 30-day default and the KUBECENTER_CHANGES_RECEIPTRETENTIONDAYS
  override are added by the Release E wiring unit (U29b), not by this
  migration. Cleanup removes receipts regardless of completion, so replay
  protection for an operation id ends at retention: after that, the same id
  inserts as a fresh receipt. change_receipt_grants rows go with their receipt
  (ON DELETE CASCADE).

Orphan reconciliation:
  ReconcileOrphans(olderThan) closes rows with state = 'applying' and
  completed_at IS NULL whose created_at is older than olderThan (the store
  exports ReceiptOrphanGrace = 10 minutes): failed when mutation_started_at IS
  NULL (the cluster was never touched), unknown when it is set (the apply was
  interrupted). It never replays anything, and never touches a previewed row
  or a row that is already terminal. The age bound is what makes it safe across
  a rolling update, where the old and new backend pods overlap (the backend
  Deployment uses the default RollingUpdate and replicaCount may be raised):
  a new pod's boot-time call cannot reap the old pod's live apply, because a
  live apply is far younger than the grace. The remaining assumption is that no
  apply runs longer than the grace; applies are bounded by the 30s BFF proxy
  cap. The wiring unit (U29b) is expected to call it at boot and again on the
  periodic retention tick so a row too young to reap at boot is reaped later.

Inspect rows that never reached a terminal state:
  SELECT id, owner_username, cluster_id, state, verification_state, created_at
    FROM change_receipts
   WHERE completed_at IS NULL
   ORDER BY created_at DESC;

Rollback:
  The down migration drops both tables and DESTROYS all receipt history;
  there is no forward path that preserves it. The Release E wiring unit
  (U29b) is expected to nil-guard every receipt access so a backend image
  containing the /changes handler returns 503 rather than crashing once the
  tables are gone; until it lands there is no handler to roll back. Roll the
  binary back first or together.

000024_create_incidents (Release D incidents, U21a, 2026-10-05)
------------------------------------------------------------------------

Creates five new tables: incidents, incident_evidence, incident_notes,
incident_note_revisions and incident_grants. Purely additive: no existing
table, column, index or row is touched. (The plan reserved 000020; 000020
through 000023 were taken by the time this landed.) U21a ships the store for
incidents and notes; evidence and grant writes arrive in U21b on top of this
same schema, so the evidence and grant tables stay empty until then.

What it stores:
  An incident record (owner, cluster, title, summary, open/closed status,
  investigation window, evidence counters, and the retention in force when
  it was created, retention_days_at_capture). Notes are the only mutable
  content: every edit bumps incident_notes.revision and copies the prior
  body into incident_note_revisions in the same transaction, so note history
  is append-only. Every child table cascades from incidents (ON DELETE
  CASCADE).

owner_id is not a local_users foreign key:
  incidents.owner_id, incident_notes.author_id and incident_grants.grantee_id
  hold auth.User.ID (provider-qualified TEXT, the nc_reads.user_id
  precedent). Deleting a local user does NOT delete their incidents, notes or
  grants; those rows stay until the incident is deleted or expires. The
  per-owner inspection query below lists incidents per owner so a removed
  account's rows can be identified.

Retention (operator footgun 1):
  Retention is configured by KUBECENTER_INCIDENTS_RETENTIONDAYS (wired by
  U25a; default 30, clamped to [1, 3650]). The sweep deletes whole incidents
  by created_at using the CURRENTLY configured value, not the value stored in
  retention_days_at_capture (that column is a forensic record only).
    - Lowering the value retroactively deletes, on the next sweep, every
      incident older than the new window, including ones created under a
      longer policy.
    - Raising it does NOT resurrect incidents that were already deleted.
  Retention is time-based only: closing an incident, deleting the Kubernetes
  object it describes, or revoking someone's access never deletes it.
    - Lowering guard (U25a): at start the backend counts incidents the
      configured value would delete although the retention they were created
      under (retention_days_at_capture) would have kept them. If there are
      any it logs a Warn (count and created_at range) and defers the first
      sweep by one hour, the window to put the old value back. Set
      KUBECENTER_INCIDENTS_RETENTIONLOWERINGCONFIRMED=true to sweep at once.
      Incidents that simply expired under their own retention are not
      counted. The Warn also reports laterAffectedIncidents: live incidents
      still inside the new window that were captured under a longer
      retention and so will be deleted earlier than promised. That count is
      reported but does not defer the sweep. Whether a start counts as a NEW
      lowering is decided from the retention the last successful sweep
      applied, which is persisted (000025 below): the deferral and the Warn
      happen once per lowering, and later restarts are steady state (no
      deferral, no Warn; laterAffectedIncidents is logged at Info). The
      confirmed flag is a one-shot acknowledgement: remove it after the
      first sweep. A process that restarts more often than hourly during an
      unconfirmed new lowering never runs its first sweep (fail safe); set
      the confirmed flag to proceed. The sweep deletes in batches of 500, so
      a large backlog is removed progressively and an interrupted sweep keeps
      its progress.
    - Multi-replica skew: every replica sweeps with its OWN configured value.
      A replica started with a lower value deletes for all of them, and
      reverting the config afterwards does not restore what it deleted. Roll
      the retention value out to every replica together; the guard above only
      protects a replica's own first hour.

Rollback (operator footgun 2):
  Do NOT just deploy the older image. Its startup migration runner sees
  version 24 recorded with no embedded 000024 file and fails with "no
  migration found for version 24" (not "no change"); the backend then starts
  with no database. The procedure is (LEAVE the incident tables in place
  throughout):
    1. Stop every backend pod running the new image, e.g. scale the backend
       Deployment to 0 replicas and wait until none is left. Any new-image
       pod that (re)starts after step 2 re-applies 000024 on boot and puts
       the version back to 24.
    2. Reset the recorded version:
         UPDATE schema_migrations SET version = 23, dirty = false;
       (or, with the golang-migrate CLI, `migrate ... force 23`).
    3. Deploy the older image and scale back up. It starts cleanly and never
       reads the incident tables.
    4. Verify: `SELECT version, dirty FROM schema_migrations;` must read
       23 | f, and the backend log must not contain "failed to connect to
       database, falling back to slog audit". If the version reads 24 again,
       a new-image pod ran in between: repeat from step 1.
  A later roll-forward to an image that includes 000024 re-runs the 000024
  up file over the tables left in place. That is harmless: every statement
  in it is CREATE TABLE / CREATE INDEX ... IF NOT EXISTS (constraints are
  inline, so they are skipped with their table) or COMMENT ON, which is
  idempotent; existing rows are kept.
  TestMigration000024_DocumentedRollbackKeepsDataAndRollsForward walks this
  procedure end to end.

  Running the down migration instead destroys every incident, its evidence,
  notes, note revisions and grants. There is no export-on-rollback path and,
  until the incident export endpoint ships (Release D U23b), no export path
  at all.

Inspect incidents:
  Per owner (identifies a removed account's rows):
    SELECT owner_id, COUNT(*), MIN(created_at), MAX(created_at)
      FROM incidents
     GROUP BY owner_id
     ORDER BY owner_id;
  Per incident:
    SELECT id, owner_id, cluster_id, created_at, evidence_count, evidence_bytes
      FROM incidents
     ORDER BY created_at;

000025_incident_retention_state (Release D incidents, U25a, 2026-10-05)
------------------------------------------------------------------------

Creates one table, incident_retention_state, holding at most one row (id is a
boolean primary key constrained to true): the incident retention in days that
the last successful retention sweep applied, and when. Purely additive; no
existing table, column or row is touched.

Why: the retention lowering guard (see "Retention" under 000024) must tell a
NEW lowering from steady state. Without a record it would defer the first sweep
and warn on every restart for as long as incidents captured under the old,
longer retention keep crossing the new window, which would teach operators to
leave KUBECENTER_INCIDENTS_RETENTIONLOWERINGCONFIRMED on permanently. With it:
  - configured days below the recorded days (or no record and some incident
    captured under a longer retention, past the window or still inside it): a
    new lowering. The first sweep is deferred one hour unless the confirmed
    flag is set, and only when incidents are past the window; with none past
    it, a Warn is logged and nothing is deferred;
  - configured days at or above the recorded days: steady state, no deferral
    and no Warn.
The row is written after every successful sweep. A failed write is logged and
the loop keeps sweeping; the next start then treats the lowering as new again.
Residual risk: if the write fails after a RAISE of the retention, the row keeps
the old, lower value (logged at Warn after every hourly sweep until the write
succeeds). While the raise stays in place this is steady state; but a later
lowering to a value still at or above the stale row is then treated as steady
state too, so it is neither deferred nor warned about. Fix the write failure
before lowering. A failed sweep records nothing either, so a lowering whose
sweeps keep failing is still treated as new on every start. It holds no user
data.

Rollback and the down migration: the down file drops only this table, leaving
every incident intact. The consequence is that the next start has no recorded
retention, so the guard uses its first-run rule: a lowering is new when some
incident was captured under a longer retention; the first sweep is deferred
only when incidents are already past the window (unless the confirmed flag is
set), otherwise a Warn is logged without deferral. If a database recorded at version 25 must run an image that embeds
only 000024, with every new-image pod stopped run both of:
    UPDATE schema_migrations SET version = 24, dirty = false;
    DELETE FROM incident_retention_state;
(or run the 000025 down file instead of the DELETE, which drops the table). The
DELETE matters: an image that embeds only 000024 has no Retainer (no
retention sweep, no guard) and never updates the row. New incidents are stamped with that image's
own retention while the row keeps its old value, so on roll-forward the next
start would treat the configured value as already applied, and a lowering made
in the meantime would not be deferred or warned about. With the row gone the first start after roll-forward uses the first-run
rule. A later roll-forward re-runs the up file over a kept table without error
(CREATE TABLE IF NOT EXISTS, COMMENT ON), but the stale row is the reason to
delete it.

with a lower value deletes for all of them. Keep KUBECENTER_INCIDENTS_RETENTIONDAYS
identical across replicas.
